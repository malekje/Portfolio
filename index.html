03 — Case studies

Platform engineering at Poulina Group

Two shared-infrastructure projects that remove recurring friction for every team building internal apps. Internal hostnames, service names and infrastructure details are deliberately left out.

Designed, built & deployedPlatform engineering

Unified API Gateway

One shared hostname that routes to every internal app's backend by path, with routes managed from an admin UI, so shipping a new app no longer starts with a DNS request.

Business problem

Every internal Poulina app has its own backend, secured with JWT for its web and mobile front ends. Each new app needed its own DNS entry registered through the network team. That slowed delivery and multiplied the infrastructure to manage.

Solution

A single shared gateway hostname that routes requests to each app's backend by path. Routes are managed through a separate admin front end, so adding an app is a route change instead of a network ticket. Built on YARP, extending my existing YARP gateway experience.

My responsibilities

End-to-end ownership: architecture of the routing model, gateway implementation on ASP.NET Core / YARP, the admin front end used to manage routes, and deployment.

Engineering considerations

  • Dynamic routing: routes and destinations are data managed from the admin UI, not hard-coded gateway config.
  • Auth stays where it was: each backend keeps validating its own JWTs, so apps adopt the gateway without rewriting security.
  • Centralized entry point: one place to observe, secure and evolve inbound traffic for internal apps.
ImpactNo new DNS entry per app · fewer network-team dependencies · one entry point for all internal backends

Poulina Store: internal mobile app store

A Play Store-style internal app store. Each subsidiary (filiale) sees and downloads only the apps it's allowed to, and updates reach devices automatically, straight from CI/CD.

Business problem

Android apps were built and sent to users as APKs by hand for every change. Across Poulina's many subsidiaries that was slow, error-prone and hard to control: who has which version, and who should have the app at all?

Solution

An internal app store where each filiale sees and installs only the apps it is permitted to use, and updates arrive automatically. Developers only touch GitLab and an admin portal; filiales never handle an APK again.

Key design decisions

  • CI/CD → store: publishing is wired to the company's GitLab CI/CD jobs, so a release is a pipeline run, not a manual upload.
  • Per-filiale access control: app visibility is scoped per subsidiary in SQL Server and enforced by the store backend.
  • SSO reuse: sign-in uses the in-house authentication system shared by all Poulina apps. No new identity silo.
  • MDM distribution: the store client itself is pushed to subsidiary devices through the company MDM.

Stack

Native Android client in Kotlin, chosen for direct, faster access to Android's package-installer and update APIs, which is what makes silent, automatic app updates practical. Backed by SQL Server, GitLab CI/CD, an admin web portal, the company MDM and the shared Poulina authentication.

GoalRemove manual APK distribution · centralized, per-filiale control of who gets which app · automatic updates
